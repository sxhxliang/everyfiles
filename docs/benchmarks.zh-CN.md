# everyfiles 性能基准与时间分析

本文记录 everyfiles 各类操作的实测耗时，解释每个数字为什么是这个量级，并说明如何在其他系统上复现。

**一句话结论：** 在 100 万条记录的索引上，几乎所有查询（子串、通配、组合过滤、翻页排序）都在 1～4 ms 内完成；索引加载是常数时间（0.2～0.4 ms，与大小无关）；建索引的耗时由平台的目录枚举系统调用决定，macOS 原生后端比通用实现快 1.7～3.6 倍（热缓存）。

> **只有 macOS 的数据是实测的。** Linux 和 Windows 的后端在本机无法运行，本文不给出任何编造的数字；第 6 节说明如何用同一套件在那两个平台上采集。

## 1. 测量方法

| 项目 | 值 |
|---|---|
| 机器 | Apple M1 Pro，8 核（含能效核），macOS 27.0.1（Darwin 27.0.0），APFS |
| 工具链 | rustc 1.98.1，`cargo build --release`（`lto = "thin"`，`codegen-units = 4`） |
| 命令 | `everyfiles bench --records 1000000 --iterations 100 --path <dir> --scan-iterations 3`，即 `scripts/bench.sh` |
| 缓存状态 | **热缓存**。真实目录扫描前用 `find` 预热页缓存和名字缓存；本文没有冷启动数据 |
| 统计量 | 查询报告 p50 / p95 / p99（100 次）；建索引与扫描报告最小值与中位数（3～5 次） |
| 合成数据 | `GeneratedScanner`：深 4 层、每层 8 个子目录、每目录约 213 个文件，共 997,053 条记录；文件名由单词表、数字、扩展名按五种模板随机拼成，平均约 15 字节；大小和 mtime 由确定性哈希生成 |

合成索引把文件系统 I/O 排除在外，测的是**装配器与查询引擎本身**；真实目录扫描测的是**平台枚举接口**。两者分开看。

**关于多次运行间的差异。** 同一用例的 p50 在不同轮次之间可相差 10%～20%（例如 `"a"` 在两轮里分别是 3.36 和 3.74 ms），p99 的波动更大。原因是 rayon 任务调度、能效核参与计算、以及后台进程。比较不同操作时请看 p50，并把 p99 当作尾部而非典型值。**计时期间不要并行运行其他 I/O**：本文有一组数据因为与一次文档写入同时进行而出现 196 ms 的离群匹配时间，重测即恢复 22 ms。

## 2. 合成索引：建立、保存、加载

997,053 条记录，常驻内存 65.0 MiB（33 字节元数据/条 + 原始名字池 + 折叠名字池）。

| 操作 | 最小 | 中位数 | 说明 |
|---|---|---|---|
| 建索引（内存扫描器，无 I/O） | 168.7 ms | 170.3 ms | ≈ 590 万条/秒。这是装配器的上限：分配 id、写两份名字池、折叠大小写 |
| 保存（63.0 MiB 文件） | 58～69 ms | — | 顺序写出各段并计算 xxh3，受磁盘写入带宽限制 |
| **加载（mmap，零拷贝）** | **0.23 ms** | 0.32 ms（p95） | 映射文件、校验 256 字节头部、按段表做边界与对齐检查。所有整块直接引用映射，只复制末尾不满一块的部分 |
| 校验负载哈希 | 6.0～6.7 ms | — | 对 63 MiB 做 xxh3-64，约 10 GB/s；`search` 默认不做（头部校验与抽查总是执行），`--verify` 开启；`stats`/`verify`/`watch` 总是校验 |

**为什么加载是常数时间。** 加载不解析任何记录。格式就是内存里数组的字节布局，`Chunked<T>` 的每个整块变成指向 mmap 的视图，页面在首次访问时按需调入。因此 66 MB 和 6 MB 的索引加载耗时几乎一样（真实目录那一节的 0.2～0.4 ms 也印证了这一点）。这就是"保存的索引仍然新鲜时 `search` 不到 1 ms 就能开始匹配"的来源。

**为什么保存比加载慢两个量级。** 保存必须把全部字节写到磁盘并哈希一遍；加载只需要让内核建立映射。这是刻意的不对称：保存发生在建索引之后和 `watch` 的定期落盘，加载发生在每次查询前。

## 3. 查询：逐类分析

100 万条记录，100 次迭代，单位 ms。

### 3.1 子串

| 查询 | 命中 | p50 | p95 | p99 |
|---|---|---|---|---|
| `"zzzqqqxxx"`（无命中） | 0 | 0.16 | 0.21 | 0.26 |
| `"final_notes"` | 129 | 0.25 | 0.34 | 0.36 |
| `""`（匹配全部） | 997,052 | 0.91 | 1.10 | 1.22 |
| `"rs"` | 39,761 | 1.01 | 1.94 | 4.78 |
| `"report"` | 56,225 | 1.05 | 1.82 | 2.20 |
| `"a"` | 490,942 | 3.36 | 5.11 | 9.97 |

**无命中的 0.16 ms 是扫描本身的代价。** 折叠名字池约 15 MB，切成 128 KiB 的任务交给 8 个核心做 `memmem` SIMD 扫描；没有命中就没有后续工作。这相当于每核约 12 GB/s 的扫描速率，是内存带宽量级的数字。

**代价随命中数线性增长，约 5～7 ns/命中。** `"a"` 命中 49 万条，比无命中多出约 3.2 ms。多出来的部分是：把命中偏移线性合并回记录 id、读 `flags` 做 tombstone 检查、把 id 推进结果向量。这个线性项是查询时间的主导项，也是为什么空查询（匹配全部但不做任何子串比较，走的是另一条 `filter_all` 路径）反而比 `"a"` 快。

**设计含义。** 对于真实使用场景——用户敲几个字母、命中几千到几万条——延迟稳定在 1 ms 左右。只有一两个字符的查询才会接近 3～4 ms，而 Everything 类工具的用户体验阈值在 10 ms 以上。

### 3.2 通配符

| 查询 | 命中 | p50 | p95 | p99 |
|---|---|---|---|---|
| `"img????.*"` | 7,509 | 0.85 | 0.95 | 0.98 |
| `"*_*.pdf"` | 7,919 | 0.89 | 0.98 | 1.07 |
| `"report*"` | 35,652 | 1.18 | 1.36 | 1.42 |
| `"*.rs"` | 39,761 | 1.33 | 1.73 | 3.05 |
| `"*a*"`（无字面量段，慢路径） | 490,942 | **6.70** | 8.83 | 16.23 |

**有预过滤的通配 ≈ 其最长字面量段的子串查询 + 幸存者的完整匹配。** `"*.rs"` 以 `.rs` 预过滤，命中集合与子串 `"rs"` 几乎相同（39,761），耗时 1.33 对 1.01 ms——多出的 0.3 ms 是对 4 万个候选跑双指针匹配器。`"img????.*"` 的字面量段是 `img`，预过滤后只剩几千个候选，所以比 `"rs"` 还快。

**慢路径是 2 倍而不是 20 倍。** `"*a*"` 没有长度 ≥ 2 的连续字面量，无法预过滤，只能对 100 万条记录各跑一次匹配器：6.7 ms，约 6.7 ns/条。它比子串 `"a"`（同样 49 万命中）慢一倍，因为每条记录都要进入匹配器而不是让 SIMD 先筛掉一半。仍在可接受范围内，但文档里把它标为慢路径是诚实的。

### 3.3 组合过滤

| 查询 | 命中 | p50 | p95 | p99 |
|---|---|---|---|---|
| `""` + 仅文件 | 992,372 | 0.92 | 1.41 | 1.80 |
| `""` + 仅文件 + 大小 1M～10M | 188,865 | 1.34 | 2.04 | 2.48 |
| `"report"` + mtime 在最新三分之一 | 19,263 | 1.03 | 1.52 | 1.89 |
| `"*.jpg"` + 仅文件 + 大小 > 25M | 38,210 | 1.74 | 2.46 | 3.13 |

**过滤器几乎免费。** 它们被编译成一个按代价排序的谓词，对每个**命中**执行一次，不会对内存再扫一遍。仅文件过滤在 99 万候选上只比空查询多 0.01 ms（读一个已在缓存里的 `flags` 字节）。大小区间多 0.4 ms，因为要额外读 `size` 数组（8 MB，99 万次随机读）。`"report"` 加 mtime 过滤与不加（1.05 ms）几乎一样：候选只有 5.6 万，过滤成本被掩盖。

**结论：** 组合条件越多，结果越少，耗时反而趋于子串扫描的基线。过滤不是性能问题。

### 3.4 排序与翻页

| 操作 | 作用于 | p50 | p95 | p99 |
|---|---|---|---|---|
| 取前 100 名（按大小倒序） | `"a"` 的 490,942 个命中 | 3.74 | 4.20 | 7.81 |
| 取前 100 名（按 mtime 倒序） | 同上 | 3.82 | 4.00 | 4.09 |
| **全量按名字排序** | 同上 | **48.5** | 58.4 | 66.6 |
| 全量按路径排序 | `"rs"` 的 39,761 个命中 | 2.71 | 4.38 | 8.10 |

这组数字解释了 `search --limit` 的实现策略。

**翻页用 `select_nth_unstable` 是 O(n)。** 从 49 万命中里挑出前 100 名只要 3.7 ms，和匹配本身同一量级。**全量排序是 O(n log n) 且比较的是字节串**：对同一批命中按名字完整排序要 48 ms，是翻页的 13 倍。因此 CLI 只在 `--limit 0` 时才全量排序；默认的 100 行页面始终走选择再排序的路径，百万命中也不会退化。

**按路径排序的代价在路径重建。** 它必须为每个命中沿 `parent` 链拼出完整路径再比较：4 万个命中 2.7 ms，约 68 ns/条。对几十万命中这会到几十毫秒，所以 `--sort path` 在文档中被标为慢选项，其余排序键都不需要重建路径。

### 3.5 拼音（特性 `pinyin`）

这一组来自 criterion（`cargo bench -p everyfiles-core --features pinyin --bench query -- pinyin`），不是 `everyfiles bench`，因为合成的 1M 索引里没有中文名字。单位 ms，取 criterion 的中位估计。

| 索引 | 查询 | p50 |
|---|---|---|
| 100 万条纯 ASCII 合成记录 | 子串 `"report"`（对照） | 0.98 |
| 同上 | 拼音 `"report"` | 1.50 |
| 同上 | 子串 `"zzzqqqxxx"`（无命中，对照） | 0.15 |
| 同上 | 拼音 `"zzzqqqxxx"` | 0.51 |
| 20 万条全中文名字 | 拼音 `"py"` / `"pysousuo"` / `"sousuo"` / `"chongqing"` | 3.5～4.1 |
| 同上 | 拼音 `"eve"`（命中名字里的 ASCII 段） | 4.4 |
| 同上 | 拼音 `"zzzqqq"`（无命中） | 3.8 |
| 同上 | 拼音 `--exact` | 1.8 |

**纯 ASCII 索引上多出的约 0.4～0.5 ms 是找高位字节的那一遍扫描。** 没有 ≥ 0x80 字节的名字不可能含汉字，其答案就是子串扫描的答案，所以拼音查询在这种索引上只比子串多一遍 SWAR 扫描，DP 一条都不跑。

**全中文索引每条记录都要过 DP，跨核心约 20 ns/条。** 20 万条约 4 ms，推算 100 万条全中文名字约 20 ms；真实目录里中文名字只占一部分，代价按比例缩小。无命中并不更快——DP 必须走完每条名字的每个字符才能确定没有匹配。`--exact` 反而更快，因为绝大多数记录在第一个字符就死掉了。

## 4. 真实目录：建索引

以下为**新开进程、两个后端交替运行、各 5 次**的结果（热缓存），这是最可信的对照方式；套件在同一进程内连续运行两个后端时，后跑的那个会受益于前者预热的内核名字缓存，第 5 节有说明。

### 4.1 `/usr`（77,256 条，1 个无权限目录被跳过）

| 后端 | 生效路径 | 最小 | 中位数 | 最大 |
|---|---|---|---|---|
| macos | `getattrlistbulk` | 94.8 ms | **97.6 ms** | 166.0 ms |
| generic | `std::fs::read_dir` + `lstat` | 167.2 ms | **169.5 ms** | 172.4 ms |

中位数之比 **1.74×**。单线程（`--threads 1`，3 次交替）：macos 247～254 ms，generic 377～384 ms，比值约 1.5×。

吞吐量：原生 8 线程约 79 万条/秒，单线程约 31 万条/秒；通用 8 线程约 46 万条/秒。

### 4.2 仓库根目录（30,528 条，含 `target/` 下大量小目录）

| 后端 | 生效路径 | 最小 | 中位数 | 最大 |
|---|---|---|---|---|
| macos | `getattrlistbulk` | 34.6 ms | **38.9 ms** | 47.9 ms |
| generic | `std::fs::read_dir` + `lstat` | 132.6 ms | **138.7 ms** | 148.9 ms |

中位数之比 **3.56×**。

### 4.3 保存与加载（两棵树）

| 树 | 索引文件 | 保存 | 加载 |
|---|---|---|---|
| `/usr`，77k 条 | 4.7 MiB | 10～11 ms | 0.24～0.37 ms |
| 仓库根目录，30k 条 | 3.1 MiB | 10～11 ms | 0.31 ms |

### 4.4 分析

**为什么原生快。** `getattrlistbulk` 一次系统调用返回一个目录里最多上万条目的名字、类型、大小、mtime、inode；通用后端对每个条目各做一次 `lstat`，系统调用数多两个量级。原生路径的瓶颈是目录数（每目录至少一次调用）而不是文件数。

**为什么两棵树的倍数不同。** `/usr` 的目录相对少而大，热缓存下单次 `lstat` 只要约 1 µs，8 个线程并行后通用后端只慢 1.7 倍；仓库根目录有上千个只装几个文件的小目录（Cargo 的 `target/` 结构），每目录的固定开销占比高，`lstat` 的次数相对条目数也更"密"，差距拉大到 3.6 倍。目录形状比条目总数更能决定通用后端的劣势。

**缓存状态对通用后端影响远大于原生后端。** 本次会话早先在一次长时间的大索引构建之后立刻用 `index` 命令扫描 `/usr`，通用后端耗时 632 ms（原生 99 ms），是热缓存下的 3.7 倍；这说明一旦内核名字缓存被挤出，逐条 `lstat` 的代价会急剧上升，而批量接口受影响小得多。这是单次观察，未做受控重复，列在这里供参考。

**同一进程内连续运行会产生伪影。** 第一版套件在同进程里先跑原生后端、再跑通用后端，得到 169 对 173 ms——通用后端几乎没有劣势。原因是原生扫描刚把 7.7 万个 vnode 全部拉进缓存，且进程里还驻留着 65 MiB 的合成索引。现版本的 `bench --path` 已改为先释放合成索引、每轮交替后端顺序；若要做严格对照，仍建议像本节一样每次新开进程。

## 4b. 真实规模：整个家目录（497 万条）

以上合成数据是 100 万条。把本机家目录 `/Users/shihua` 整个建成索引，是第一次在真实规模上检验：

| 项目 | 值 |
|---|---|
| 记录数 | 4,969,621（目录 1,159,885，文件 3,754,323，符号链接 55,232） |
| 无法读取的目录 | 1（受 TCC 保护） |
| 内存 | 369 MiB（约 74 字节/条：33 字节元数据 + 两份平均约 20 字节的名字） |
| 索引文件 | 368 MiB，保存 418～430 ms |
| **建索引（原生后端）** | **46.0 s / 46.6 s**（两次），约 10.8 万条/秒 |

### 建索引为什么是 46 秒

按顶层子树分别计时（原生后端，热缓存）：

| 子树 | 记录 | 目录 | 耗时 | 条/秒 |
|---|---|---|---|---|
| `~/Code` | 1,146,566 | 158,663 | 5.85 s | 196k |
| `~/Library` | 909,128 | 93,887 | 6.23 s | 146k |
| `~/Documents` | 172,430 | 22,291 | 0.81 s | 212k |
| `~/.cargo` | 138,170 | 21,406 | 0.76 s | 181k |
| `~/.rustup` | 145,208 | 4,939 | 0.67 s | 218k |
| `~/Downloads` | 35,758 | 3,228 | 0.15 s | 239k |
| 整个家目录 | 4,969,621 | 1,159,885 | 46.0 s | **108k** |

单个子树能到 15～24 万条/秒，`~/Code` 的 115 万条用 5.85 秒，正好落在方案预估的"热缓存每百万 3～15 秒"区间内。但整体只有 10.8 万条/秒，比任何一个子树都慢，原因是内核的 vnode 缓存上限：

```
kern.maxvnodes: 250241      kern.num_vnodes: 250241（已满）
索引条目数:    4969621
```

这台机器最多缓存 25 万个 vnode，而家目录有近 500 万个条目。单个子树的工作集能部分留在缓存里，整树扫描则注定大部分目录的打开和 `getattrlistbulk` 都要从 APFS 读元数据——这是磁盘元数据 I/O 的速度，不是实现的瓶颈，两次 46 秒的高度一致也说明它是稳定的下限。同一子树上通用后端 9.45 s 对原生 5.85 s（1.6×）。

这正是方案开头指出的平台差距：Everything 在 NTFS 上顺序读 MFT，不需要逐目录打开，所以几百万文件只要几秒；macOS 和 Linux 没有等价物，首次建索引受目录遍历限制。而日常使用——加载已保存的索引、查询、`watch` 增量维护——不受这个限制。

### 查询（热态，索引已在页缓存中）

| 查询 | 命中 | open | match | sort |
|---|---|---|---|---|
| `Cargo.toml --exact` | 3,913 | 5～8 ms | 5～8 ms | 0.3～0.5 ms |
| `'*.pdf' --files-only --sort size --desc` | 3,557 | 5 ms | 4.7 ms | 0.2 ms |
| `'' --files-only --after -24h --sort mtime --desc` | 178,748 | 5 ms | 5.1 ms | 1.6 ms |
| `a`（单字母，最坏情况）取前 3 名，按名 | 2,549,188 | 5～12 ms | 22～29 ms | 17～29 ms |
| `a --sort mtime --desc` 取前 3 名 | 2,549,188 | 9 ms | 24 ms | 23 ms |
| `a --sort size --desc` 取前 3 名 | 2,549,188 | 5 ms | 24 ms | 22 ms（该列冷时 102 ms） |
| `a --limit 0 --sort name -o null`：全量排序并输出 255 万条路径 | 2,549,188 | 5 ms | 29 ms | 207 ms，输出 311 MB 用 1.23 s |

`open` 一列包含 mmap 加载（约 1 ms 以内，与 100 万条时一样是常数）、卷身份校验和 16 条随机抽查。有两条结论：

- **典型查询端到端 10～15 ms**，其中匹配本身 5 ms——5 倍的数据量，匹配时间与 100 万条时（约 1 ms）成比例增长，符合"扫描成本与池大小线性"的模型。
- **单字母查询热态约 50～60 ms**：255 万命中，匹配 22～29 ms（约 9～11 ns/命中），再对任一排序键取前 3 名 17～29 ms。这是交互场景能遇到的最坏情况；全量排序这 255 万命中要 207 ms，而把它们全部输出（311 MB）要 1.2 s，所以默认 `--limit 100` 走选择算法而不是全量排序。
- **每一列数组首次触碰要多付 60～80 ms。** `size` 和 `mtime` 各是 40 MB 的 mmap 列，只有用到对应排序键或过滤器的查询才会读它们；若这些页不在页缓存里，第一次按 mtime 排序测到 81 ms、按 size 排序 102 ms，热态后都回到 22～23 ms。这是零拷贝加载的直接后果：没有被读过的列根本不在内存里。

### 这次测量带来的两处改进

1. **抽查并行化。** 第一版 `open` 在 12～57 ms 间波动。原因不是加载，而是 16 次随机 `stat` 串行执行：在 vnode 缓存装不下的树上，每次都是冷路径查找。改为 rayon 并行后 `open` 稳定在 5～8 ms。
2. **按名字排序先比 8 字节前缀。** 对 255 万命中按名字取前 3 名原来要 53 ms——每次比较都要两次随机读名字池。现在先把折叠名字的前 8 字节作为大端整数键（名字不含 NUL，零填充与字典序一致），只在前缀相同时才比较全名，降到 17～29 ms，与按整数列（size、mtime）排序同一量级。

### 页缓存：首次查询可能慢一个量级

索引文件是磁盘上的缓存。在它被其他 I/O 挤出页缓存后（例如刚对几百万文件做过扫描），第一次查询要为触及的每一页付磁盘代价：

```
run 1   open 56.8 ms   match 97.4 ms   sort 16.9 ms    ← 页缓存已被挤出
run 2   open  —        match  5.1 ms   sort  0.3 ms    ← 页已常驻
run 3   open 29.4 ms   match  5.0 ms   sort  0.3 ms
```

这是 mmap 零拷贝设计的另一面：加载不复制数据，所以数据何时进入内存取决于页缓存。随后的查询恢复到毫秒级。`search --verify` 在这种状态下会对 368 MiB 做一次完整读取加哈希，耗时 619 ms；因此负载哈希改为 `search` 的可选项（`--verify`），`stats`/`verify`/`watch` 仍然总是校验。

## 5. 各操作的量级速查

| 操作 | 100 万条索引上的典型值 | 复杂度 |
|---|---|---|
| 加载已保存索引 | 0.2～0.4 ms | O(1)，与大小无关 |
| 无命中查询 | 0.16 ms | O(池大小)，SIMD 扫描 |
| 几千到几万条命中 | 0.3～1.3 ms | 扫描 + 约 5～7 ns/命中 |
| 单字符查询（约 50 万命中） | 3～4 ms | 同上 |
| 带预过滤的通配 | 0.9～1.3 ms | 子串成本 + 候选的匹配器 |
| 无字面量段的通配 | 6～7 ms | O(记录数) 匹配器 |
| 组合过滤 | +0～0.4 ms | 每命中一次谓词 |
| 取前 100 名 | 3～4 ms（49 万命中） | O(n) 选择 |
| 全量按名排序 | 48 ms（49 万命中） | O(n log n) |
| 建索引（内存扫描器） | 170 ms | ≈ 590 万条/秒 |
| 建索引（macOS 真实目录，工作集放得进 vnode 缓存） | 15～80 万条/秒 | 受目录数与系统调用限制 |
| 建索引（macOS，497 万条整个家目录） | 10.8 万条/秒，46 s | 超过 vnode 缓存上限后为磁盘元数据 I/O |
| 497 万条索引上的典型查询 | 10～15 ms 端到端，匹配 5 ms | 与池大小线性 |
| 497 万条索引上的单字母查询 | 约 50～60 ms（热态） | 255 万命中；某列冷时再加 60～80 ms |
| 保存 | 约 1 ms / MiB | 磁盘写入 + 哈希 |

## 6. 在 Linux 与 Windows 上采集

本机无法运行这两个后端，CI 上可以。

**方式一：GitHub Actions 产物。** 工作流中的 `bench-report` 任务在 `ubuntu-latest`、`macos-14`、`windows-latest` 上各跑一遍 100 万条合成套件加 `crates/` 目录的真实扫描，把人类可读文本和 JSON 作为 `bench-<os>` 产物上传。注意 GitHub 托管的 runner 是共享虚拟机，绝对数值会明显低于本文的 M1 Pro，并且轮次间波动更大；它们适合看**相对关系**（各类操作之间、原生与通用之间），不适合与本文的绝对值直接比较。

**方式二：本地运行。**

```sh
scripts/bench.sh <真实目录> [记录数] [迭代次数]
# 或
cargo build --release -p everyfiles-cli
target/release/everyfiles bench --records 1000000 --iterations 100 --path <真实目录> --json
```

**采集时请注意的平台差异（不是预测数值，是已知的行为差异）：**

- **Linux 默认不采集大小和 mtime。** `getdents64` 只给名字和类型，所以默认扫描比 macOS 少做一部分工作，但索引里 `size/mtime` 覆盖率为 0，大小与时间过滤会把所有条目排除。加 `--with-stat` 后每条目多一次 `statx`，扫描会显著变慢，才能与 macOS 的数字可比。请分别采集两种模式。
- **Linux 的 `d_type == DT_UNKNOWN`**（无 `ftype` 的 XFS、不少 NFS）会让每个这样的条目多一次 `statx`，扫描变慢的幅度取决于文件系统。
- **Windows 的扫描总是走非特权的 `FileIdBothDirectoryInfo` 遍历**，它已经批量返回大小和 mtime，与 macOS 可比；USN 日志只用于监听，不影响建索引时间。管理员与非管理员的 `index`/`search` 耗时应当相同。
- **通用后端（`--backend generic`）在三个平台上的实现一致**，是跨平台比较时最稳定的参照。
- 预热：脚本会先 `find` 一遍目录，使页缓存和名字缓存处于热状态，与本文一致。要测冷启动需要自行清缓存（Linux 用 `echo 3 > /proc/sys/vm/drop_caches`，需 root）。

## 7. 复现本文的全部数据

```sh
# 第 2、3 节：合成索引与查询（也产出第 4 节的 /usr 数据，但建议用下面的受控方式）
scripts/bench.sh /usr 1000000 100

# 第 4 节：受控的扫描对照，新开进程、交替后端、各 5 次
for i in 1 2 3 4 5; do
  for b in macos generic; do
    target/release/everyfiles index /usr --backend $b --index /tmp/cmp-$b.idx --json \
      | python3 -c 'import sys,json; print(json.load(sys.stdin)["elapsed_ms"])'
  done
done

# 单线程
target/release/everyfiles index /usr --backend macos   --threads 1 --json
target/release/everyfiles index /usr --backend generic --threads 1 --json
```

`--json` 输出里的 `elapsed_ms` 即建索引耗时，`index_bytes`/`save_ms` 为保存信息；`search --stat` 会在 stderr 打印单次查询的打开、匹配、排序、输出四段耗时。
